# Immutable application dependencies

`marcmy/VideoRenderer-Dependencies` stores the runtime and model assets used by this application's installer. It is not a general SDK mirror. NVIDIA components retain their own terms; the renderer's GPL does not relicense them. The packages include the original license notices and component provenance. TensorRT/CUDA packages contain runtime DLLs, not SDK compilers or developer tools. Maxine's native libraries retain the Software License Agreement and AI product terms supplied with the pinned NVIDIA package. Prepared RIFE models carry their original model license and source/checksum manifest.

Each component release is addressed by its build recipe hash. Runtime source, compiler/runtime versions, SDK archive hashes, model transformations and source pins participate in that identity. Renderer-only changes do not. An existing immutable tag must match every asset's size/hash; publication refuses different content and never overwrites an asset. Unchanged component releases are reused. The renderer commits `dependencies.lock.json`, including exact release tags, asset URLs, sizes, SHA-256 hashes, compatibility and original provenance.

Dependency publishing is separate: `./dev.ps1 dependencies -Component rife-runtime` (or `rife-models`, `maxine`) dispatches the dependency repository's manual workflow using the developer's existing GitHub authentication. Its own `GITHUB_TOKEN` writes only to that repository. The main renderer workflow has no cross-repository write credential. If fully automatic dispatch from the main repository is later wanted, a narrowly scoped GitHub App token for Actions dispatch in the dependency repository would be needed; no broad PAT is embedded or required for normal renderer releases.

The dependency repository's `.github/workflows/publish.yml` is maintained from `tools/Dev/DependencyRepository.yml`. It builds only the selected changed component, validates it, and exposes the release after server digest verification. The reusable runtime/model builders remain in the renderer source repository so their recipes stay beside the native API and conversion tools. Publication runs only on the dependency repository's `main`. Its trusted configuration grants one literal reviewed source SHA to every checkout and both reusable workflow references. The manual `source_ref` must match that grant before planning; it never selects executable code. Builders, recipe hashing and publishing therefore use the same immutable source and workflow definitions, even if renderer master advances.

`./dev.ps1 dependencies` is an explicit maintainer approval/publication operation: after reviewing clean committed source and pushing it, run the command using GitHub credentials that can edit workflows in the dependency repository. It fetches source state, commits the rendered source/recipe grant to dependency `main` using the existing file's blob SHA as a concurrency guard, then dispatches that approved build. A repeated grant is a no-op; conflicting edits fail safely. No credential is embedded or handed to the build. An authorized dispatcher cannot substitute another SHA without independently obtaining workflow-file write authority. Review-branch recipe publication remains supported so its verified lock update can pass renderer CI before merge. The runtime/model asset resolution never uses `latest`.

For pre-merge experiments without publication approval, push a review branch and run `gh workflow run rife-runtime.yml --repo marcmy/VideoRenderer --ref <review-branch>` or the corresponding `rife-model.yml` command. These existing builders run in that branch's context with read-only repository permissions and produce CI artifacts, not dependency releases. SDK cache keys include the caller repository and ref; cached archives still require pinned SHA-256 verification. Test Maxine packaging locally with `python tools/MaxineRuntimeInstaller/Build-MPCVRMaxineRuntime.py --output <new-directory>`. Approve and publish a reviewed recipe separately, then update the lock after its immutable release is verified.

After a successful dependency update, run `python tools/Dev/dependencies.py plan --directory _artifacts/dependency-plan`, then `python tools/Dev/dependencies.py lock --directory _artifacts/dependency-plan --output dependencies.lock.json`. Review and commit the new pins. Normal CI fails if a build recipe has changed without a matching lock update.

The initial migration preserves the last verified public binary bytes from `bea5902b1a98488fce1cfc9df9480d388a6bc2af`. It does not rebuild them. Their original renderer/runtime release references and SHA-256 hashes remain in the component manifests. Historical main-repository releases remain untouched until the separate cleanup plan is approved.
