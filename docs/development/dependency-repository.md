# Immutable application dependencies

`marcmy/VideoRenderer-Dependencies` stores the runtime and model assets used by this application's installer. It is not a general SDK mirror. NVIDIA components retain their own terms; the renderer's GPL does not relicense them. The packages include the original license notices and component provenance. TensorRT/CUDA packages contain runtime DLLs, not SDK compilers or developer tools. Maxine's native libraries retain the Software License Agreement and AI product terms supplied with the pinned NVIDIA package. Prepared RIFE models carry their original model license and source/checksum manifest.

Each component release is addressed by its build recipe hash. Runtime source, compiler/runtime versions, SDK archive hashes, model transformations and source pins participate in that identity. Renderer-only changes do not. An existing immutable tag must match every asset's size/hash; publication refuses different content and never overwrites an asset. Unchanged component releases are reused. The renderer commits `dependencies.lock.json`, including exact release tags, asset URLs, sizes, SHA-256 hashes, compatibility and original provenance.

Dependency publishing is separate: `./dev.ps1 dependencies -Component rife-runtime` (or `rife-models`, `maxine`) dispatches the dependency repository's manual workflow using the developer's existing GitHub authentication. Its own `GITHUB_TOKEN` writes only to that repository. The main renderer workflow has no cross-repository write credential. If fully automatic dispatch from the main repository is later wanted, a narrowly scoped GitHub App token for Actions dispatch in the dependency repository would be needed; no broad PAT is embedded or required for normal renderer releases.

The publisher's source/security structure is maintained from `tools/Dev/DependencyRepository.yml`; the dependency repository owns its external action pins. Approval preserves those reviewed full-SHA action references and restores the template's source and permission controls. The workflow builds only the selected changed component, validates it, and exposes the release after server digest verification. Reusable runtime/model builders remain beside the renderer's native API and conversion tools. Publication runs only on dependency `main` or a matching `dependency-source-<approved-SHA>-<configuration-digest>` approval tag. Its trusted configuration grants one literal reviewed source SHA to every checkout and both actual reusable workflow definitions. The manual `source_ref` must match that grant before planning; it never selects executable code.

`./dev.ps1 dependencies` is an explicit maintainer approval/publication operation: after reviewing clean committed source and pushing it, run the command using GitHub credentials that can edit this repository's workflow configuration. It fetches source state, commits the rendered grant using the current workflow blob SHA as a concurrency guard, pins that exact configuration with a source SHA plus configuration digest, then dispatches through the tag. Concurrent approvals cannot switch a request's configuration. Matching grants are reused; conflicting edits/tag content fail safely, and tags are never moved or replaced. A reviewed action update produces a new configuration identity even for the same renderer source. Older approval tags remain intact. No credential is embedded or handed to the build. Review-branch recipe publication remains supported before its verified lock update passes renderer CI.

The dependency repository has grouped weekly Dependabot action updates, with renderer reusable-workflow pins excluded. Its small YAML-validation dependency is updated separately. Fast read-only PR/push validation checks syntax, source bindings, action pins, credential persistence and permission boundaries; it never packages runtimes. Main is protected against deletion/force pushes and approval tags against update/deletion, while normal source approvals may still create configuration commits and new tags. Repository token defaults are read-only; only the publisher explicitly requests content writes. SHA enforcement is performed by validation so historical approved workflow snapshots with older action tags remain reproducible under the allowed-official-actions policy.

For pre-merge experiments without publication approval, push a review branch and run `gh workflow run rife-runtime.yml --repo marcmy/VideoRenderer --ref <review-branch>` or the corresponding `rife-model.yml` command. These existing builders run in that branch's context with read-only repository permissions and produce CI artifacts, not dependency releases. SDK cache keys include the caller repository and ref; cached archives still require pinned SHA-256 verification. Test Maxine packaging locally with `python tools/MaxineRuntimeInstaller/Build-MPCVRMaxineRuntime.py --output <new-directory>`. Approve and publish a reviewed recipe separately, then update the lock after its immutable release is verified.

After a successful dependency update, run `python tools/Dev/dependencies.py plan --directory _artifacts/dependency-plan`, then `python tools/Dev/dependencies.py lock --directory _artifacts/dependency-plan --output dependencies.lock.json`. Review and commit the new pins. Normal CI fails if a build recipe has changed without a matching lock update.

The initial migration preserves the verified public binary bytes from `bea5902b1a98488fce1cfc9df9480d388a6bc2af`, with original renderer/runtime release references and hashes retained in component manifests. Approved historical renderer-release cleanup is separate from immutable dependency retention.
